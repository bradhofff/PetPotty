# PetPotty health platform audit and MVP plan

Audit date: 2026-09-10

This document records the repository and configured test-schema review performed before the health-history MVP was implemented. The application and SQL schema—not the product brief—were treated as the source of truth.

## A. Current architecture summary

### Application shape

- ASP.NET Core 10 Razor Pages application with page models in `Pages`.
- Hand-written ADO.NET services using `Microsoft.Data.SqlClient`; Entity Framework packages are referenced but there is no `DbContext`, entity mapping, or EF migration set.
- SQL Server changes are deployed as dated, idempotent scripts in the unusually named `Migrationsss` directory. Existing services use a mixture of stored procedures and parameterized inline SQL.
- `Home` is the dashboard and pet/task-management page. `Medications` owns medication definitions and generated schedule rows. `VetVisits` owns appointments, reminders, outcomes, history, and documents.
- Bootstrap, a shared layout, page-local JavaScript, and `wwwroot/css/site.css` provide the current responsive orange/neutral visual system and dark mode.

### Models and tables

| Area | Application model | SQL source | Notes |
| --- | --- | --- | --- |
| Accounts | Page-bound fields only | `Users` | Includes profile, plaintext `pass`, admin flag, and dark-mode preference. |
| Pets | `Pet` | `Pets` | A pet has one `userID` owner. The `Pet.Age` string does not match the database's nullable integer exactly. |
| Daily care | `TaskItem` | `Tasks` | Generic `taskType`, notes, and local `createdAt`; UI types include Pee, Poop, Pee & Poop, Food, Walk, Play, and custom care. |
| Medications | `Medication`, `MedSchedule` | `Medications`, `MedicationSchedule` | Recurrence rows are generated by stored procedure. Completion is only `isConfirmed` plus `confirmedAt`. |
| Vet care | `VetVisit`, `VetVisitDocument`, `VetVisitHistory` | `VetVisits` and related tables | Visits have scheduling, outcome, reminder, soft-delete, history, and authorized document support. Legacy SQL columns include Weight and Temperature, but current models/queries/forms do not expose them. |

### Authentication and authorization

- Login establishes in-memory session keys (`userID`, name, theme). Cookie authentication is registered but login does not create an authentication principal.
- The current modified worktree contains an authorization hardening pass. Pet/task/medication/vet mutations validate the session user and scope SQL to the pet owner. Protected photo/document reads also validate ownership. The retained authorization audit reports 60 cross-account denial cases and 27 owner controls passing.
- The trustworthy identity source is currently the server session. The extra `userID` browser cookie is not used as authorization identity.
- Authorization is still ownership-based (`Pets.userID`), not membership-based. That must be changed consistently across every service before household sharing is enabled.

### Medication scheduling

- Frequencies are Hourly, Daily, Weekly, and Monthly with an interval.
- `TimingDoesNotMatter` preserves calendar-day dosing for non-hourly medication. Hourly medication is always exact-time.
- `EnsureMedicationScheduleGenerated` materializes schedule rows. Confirming an exact-time dose intentionally shifts later unconfirmed occurrences until the next confirmed anchor. This behavior must be preserved.
- Old unconfirmed doses intentionally remain visible. There is no skipped/missed state, reason, attribution, or UTC administration timestamp.

### Timezone behavior

- Existing tasks, medication schedules, vet appointments, and reminders are stored as timezone-unspecified local wall-clock values.
- Pages and SQL use `DateTime.Now`, `DateTime.Today`, `SYSDATETIME()`, and `GETDATE()`. On a VPS these can produce the wrong user day and overdue state.
- Browser `datetime-local` values contain no offset. There is no user timezone profile or browser-offset cookie.
- Existing local rows cannot be safely reinterpreted as UTC without knowing the user's historical timezone. The safe transition is to keep legacy columns intact, store new clinical timestamps in UTC, capture the browser offset, and normalize legacy rows only in read projections.

### Files, reporting, and household concepts

- Pet photos use validated JPEG/PNG filesystem storage behind `IPetImageStorage`, with an owner-checked Razor endpoint.
- Vet documents use validated PDF/Word/JPEG/PNG filesystem storage behind `IVetVisitDocumentStorage`, store metadata in SQL, and are owner-checked on preview/download.
- There is no health-event media relation, object-storage provider, report/export service, trend service, household membership, invitation, or caregiver role.

## C. Recommended data model

### MVP

```text
Users ──< Pets ──< HealthEvents
                  ├─ EventKind: Symptom | Incident
                  ├─ EventType, OccurredAtUtc, EndedAtUtc, Severity
                  ├─ Description, PossibleTrigger
                  ├─ AppetiteStatus, DrinkingStatus
                  ├─ RelatedMedicationID (nullable)
                  ├─ RecoveryStatus, RecoveredAtUtc, VeterinarianContacted
                  └─ CreatedByUserID, CreatedAtUtc, UpdatedAtUtc

Pets ──< Medications ──< MedicationSchedule
                            ├─ existing scheduleDate/isConfirmed/confirmedAt
                            └─ DoseStatus, AdministeredAtUtc, RecordedAtUtc,
                               RecordedByUserID, StatusReason, AdministrationNotes

Tasks.RecordedByUserID and VetVisits.CreatedByUserID
  = additive attribution for existing/new timeline sources

HealthTimelineItem (read model only)
  = HealthEvents UNION MedicationSchedule UNION VetVisits
```

Symptoms and incidents share one table because their structured fields and lifecycle overlap. The discriminator remains understandable in SQL and C#, avoids one-to-one detail joins, and permits future event types without copying every common column. Check constraints retain data quality.

### Later additive extensions

```text
HealthEvents ──< HealthEventAttachments >── external storage object
Medications ──< MedicationHistory
Pets ──< PetMembers >── Users
Pets ──< PetConditions ── ConditionTemplates
```

`HealthEventAttachments` should contain SQL metadata, an opaque provider/key, content type, size, uploader, and UTC upload time. Local disk can be one provider; production object storage can be another. Large video bytes should not be stored in SQL Server.

## D. Recommended navigation and product hierarchy

- Keep the primary navigation to **Dashboard**, **Health**, **Medications**, and **Vet Visits**.
- **Dashboard = record and act.** It remains the daily-care landing page, keeps the existing Add Task workflow, and adds a nearby pet-specific “Log Health Event” quick action that lets the user choose Symptom or Incident without first leaving the dashboard.
- **Health = review and understand medically.** It contains a concise medication/adherence/recent-event/vet overview, a medical-only timeline over health events, dose statuses, and vet visits, pet/date/source filters, fast “Log symptom” and “Log incident” actions, and the entry point for vet-report generation. Routine `Tasks` stay on Dashboard.
- **Vet Report = summarize and share.** Report range selection belongs on Health. A dedicated authorized Razor endpoint may render the printable result, but Reports is not a top-level navigation destination in the MVP.
- The Dashboard and Health logging actions post through the same HealthEvent handler/service so validation, authorization, attribution, and UTC conversion do not diverge.
- Keep **Medications** and **Vet Visits** as focused workflows. Do not add caregiver navigation until membership is consistently enforced; a future pet/household settings area is a better home for invitations and roles.

## F. MVP implementation boundaries

The first implementation covers structured symptoms/incidents, the aggregated timeline, adherence status/attribution, and printable 30/90/custom reports. It intentionally does not enable sharing, upload health videos, add medication history, send notifications, diagnose trends, or expose public veterinarian links. Those capabilities require separate authorization, storage, and operational decisions and should not be represented by fake integrations.

The migration is additive and preserves existing rows. Confirmed schedule rows are backfilled as Taken; historical UTC administration time remains null because it cannot be reconstructed reliably. Existing task and visit creator IDs are backfilled from the only account that could own the pet under the current single-owner model. Legacy medication/visit wall-clock timestamps are normalized only for a requesting browser's health timeline/report projection. Task attribution remains useful to Dashboard history but Tasks are not projected into Health.
